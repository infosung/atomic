# Release Notes: `v0.2.0`

## Summary

`v0.2.0` is the current minor release for the active pre-`1.0` line.

This is the first published release after `v0.1.2`, and it consolidates the previously mainline-only
`0.1.3` draft scope into an actual tagged release while also shipping the OAuth redirect/PKCE
foundation changes that landed after `v0.1.2`.

The headline changes are:

- Spring-free `atomic.crypto`
- JWT signing-key rotation in `atomic.spring.security`
- PKCE-aware public OAuth models in `atomic.spring.oauth2`
- richer relay payload / resolved identity handoff in `atomic.app.oauth.redirect`
- current release docs and workflow examples aligned to the real `v0.2.0` line

Canonical release note path: `docs/release-notes/v0.2.0.md`

## Compatibility Baseline

- Java `25`
- Kotlin `2.3.10`
- Spring Boot `4.0.5`

## Release Highlights

### New crypto utility module

- introduces `atomic.crypto` as a standalone, Spring-free helper module
- provides Base64Url, HMAC, HKDF, PBKDF2, AES-256-GCM, and versioned envelope helpers
- adds context-bound payload helpers:
  - `AeadEnvelopeContext`
  - `ContextBoundEncryptedPayload`
  - `ContextBoundAeadEnvelopeCipher`
- binds `ownerId`, `purpose`, sorted metadata, `cryptoVersion`, and `keyVersion` into AEAD
  associated data so stored payloads fail closed when context drifts
- envelope decryption resolves keys by embedded `keyId`, which keeps current/previous key
  resolution Spring-free and host-managed
- keeps JWT/security-adjacent primitives reusable outside Spring-specific auto-configuration

### Security key rotation support

- `atomic.spring.security.JwtProvider` now accepts optional previous signing keys for verification
- signing remains pinned to the current key
- previous keys are verification-only lanes for safe secret rotation
- newly issued tokens now include JWT `kid`
- configuration uses `access-key-id`, `refresh-key-id`, `previous-access-keys`, and
  `previous-refresh-keys`

### OAuth foundation and relay handoff upgrades

- `atomic.spring.oauth2` now exposes caller-managed PKCE fields explicitly:
  - `OauthAuthorizationRequest.codeChallenge`
  - `OauthAuthorizationRequest.codeChallengeMethod`
  - `OauthTokenExchangeRequest.codeVerifier`
- `OauthIdentityResult` is richer and now exposes `providerSubject`, `emailVerified`,
  `selectedClientKey`, and `normalizedProfileMetadata`
- `atomic.app.oauth.redirect` keeps the browser/server relay model and now hands the host app a
  richer `relayCode` payload with optional `resolvedIdentity`
- the intended platform story is now explicit across web, iOS, Android, macOS, and Windows
- final login, account binding, and session issuance still remain host-application responsibilities

### Release-line alignment

- current README and usage guides now point to the real `v0.2.0` line
- current artifact examples move from `0.1.2` to `0.2.0`
- release entry docs now point to the dedicated `v0.1.2` -> `v0.2.0` migration guide
- workflow input examples now reference `v0.2.0`
- `v0.1.3` remains an unpublished draft line only; no `v0.1.3` tag was released

### Published/runtime scope remains stable

The public app, security, and event-log runtime scope remains intact:

- `atomic.event.log.ingest.api` remains the official HTTP ingest API module
- relational DB support continues to cover `postgresql`, `mysql`, `mariadb`, and `oracle`
- `h2` remains test-compatibility only
- `atomic.app.oauth.redirect` still keeps the `JPA-backed` default path and the custom-table
  `legacy JDBC` fallback path

## Recommended Host Action

1. bump Atomic artifacts to `0.2.0`
2. if you need standalone crypto helpers or JWT rotation primitives, add `atomic.crypto`
3. if you adopt the new context-bound payload helpers, persist the full
   `ContextBoundEncryptedPayload` contract and keep `keyVersion` unchanged across storage and
   decrypt paths
4. if you rotate JWT secrets, configure `access-key-id` / `refresh-key-id` and keep
   `previous-access-keys` / `previous-refresh-keys` as verification-only lanes
5. if you use OAuth redirect relay, review PKCE handling and consume `resolvedIdentity` /
   `providerSubject` in your login API rather than reparsing provider payloads later
6. if your host still pins Spring Boot `4.0.3`, move to `4.0.5`
7. if you previously followed mainline docs labeled `0.1.3`, treat `0.2.0` as the first tagged
   release that contains that scope
