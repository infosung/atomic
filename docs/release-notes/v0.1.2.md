# Release Notes: `v0.1.2`

## Summary

`v0.1.2` is the current patch release for the `0.1.x` line.

This release does not introduce a new module family after `v0.1.1`.
Instead, it aligns the active release line so that current documentation, CI semantics, and release automation all match the already-shipped secure baseline.

## Compatibility Baseline

- Java `25`
- Kotlin `2.3.10`
- Spring Boot `4.0.5`

## Patch Highlights

### Release-line alignment

- current README and usage guides now consistently point to the `v0.1.2` line
- current artifact examples move from `0.1.1` to `0.1.2`
- current release entry docs now point to the dedicated `v0.1.1` -> `v0.1.2` migration guide

### Secure baseline continuity

The recommended secure production baseline remains Spring Boot `4.0.5`.

This matters because:

- the release line still tracks the Spring fixes for `CVE-2026-22732`
- the release line still tracks the Spring fixes for `CVE-2026-22735`
- hosts still pinned to `4.0.3` should move to `4.0.5` to stay on the fixed Spring Framework `7.0.6` / Spring Security `7.0.4` line

### CI and release automation hardening

- compatibility CI now keeps exactly one secure baseline lane for Spring Boot `4.0.5` / Kotlin `2.3.10`
- non-baseline lanes are isolated from the secure-baseline contract
- repository workflows now use Node 24 compatible action majors such as `actions/checkout@v5`
- tag-and-release now requires a curated release notes file instead of relying on generated notes only

### Published/runtime scope remains stable

The public module and runtime scope from `v0.1.1` remains intact:

- `atomic.event.log.ingest.api` remains the official HTTP ingest API module
- relational DB support still covers `postgresql`, `mysql`, `mariadb`, and `oracle`
- `h2` remains test-compatibility only
- `atomic.app.oauth.redirect` still keeps the `JPA-backed` default path and the custom-table `legacy JDBC` fallback path

## Recommended Host Action

1. bump Atomic artifacts to `0.1.2`
2. if you already run `0.1.1` on Spring Boot `4.0.5`, no public runtime migration should be needed
3. if your host still pins Spring Boot `4.0.3`, move to `4.0.5`
4. review the current patch migration guide before rollout
