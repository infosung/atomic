# Migration Guide: `v0.0.1` -> `next`

> Status: Draft for in-progress work.
> This document tracks user-facing migration impact before the next release is cut.

## Who Should Read This

Read this guide if you are currently on `v0.0.1` and use any of these:

- `atomic.app`
- `atomic-app:oauth-redirect`
- `atomic.starter` + `atomic.spring.oauth2` with app-level oauth redirect flow

If you only use `atomic.storage`, `atomic.spring.web`, `atomic.spring.security`, `atomic.spring.idempotency`, or `atomic.heartbeat`, there is currently no migration item in this draft from this workstream.

## Summary

Current in-progress contract changes from `v0.0.1` are concentrated in `atomic-app:oauth-redirect`, with targeted schema/delete changes in `atomic-app:storage-api` and `atomic-app:app-version`.

### Breaking or Behavior-Changing Items

| Area | `v0.0.1` | `next` draft | Impact |
|---|---|---|---|
| Google/Kakao callback state handling | query callback verified state without consuming it | query callback consumes state via one-time verification | repeated callback/state reuse now fails |
| Callback-binding cookie lifecycle | callback-binding cookie could remain after success | successful callback clears the cookie immediately | flows relying on cookie reuse must restart from redirect |
| Redirect API enablement | `atomic.app.oauth.redirect.enabled=true` could leave endpoints absent when oauth beans were missing | startup now fails fast unless required oauth beans exist | misconfigured apps fail earlier |
| Replay protection prerequisite | `OauthStateManager` without backing store could still be used | oauth redirect now requires store-backed `OauthStateManager` | state store strategy must be explicit |
| Cache relay consume guarantee | cache relay consume relied on cache `get(...)` + `evict(...)` and did not constrain backend capabilities | cache relay store now requires an atomic remove-and-return backend, otherwise startup fails or falls back according to `store.fail-fast` | cache backend choice must be reviewed before enabling `store.type=cache` |
| Redirect allowlist validation timing | malformed allowlist entries could fail on first request | malformed entries now fail startup | config must be fixed before deploy |
| App module `HttpStatusException` wire mapping | host-app exception advice was effectively required to guarantee documented `400/403/404` responses | app module controllers now ship built-in `HttpStatusException` mapping | apps without custom advice now get the documented status/envelope by default; apps with custom advice should verify precedence |
| Image delete storage resolution | delete could fall back from persisted `storageType` to path-based backend resolution | delete uses persisted `storageType` only and returns `400` when that mapping is unavailable | renaming/removing storage client keys can break delete for existing image rows until metadata is migrated |
| Image delete workflow | metadata row was deleted in the same path without an explicit retryable state | delete now reserves metadata as `DELETE_PENDING`, deletes storage, and purges metadata only after storage cleanup succeeds | failed storage deletes now leave retryable `DELETE_PENDING` rows instead of pretending the delete fully completed |
| Image upload response model | controller/source contract exposed `BaseResponse<ImageEntity>` | controller/source contract now exposes `BaseResponse<ImageResponse>` with the same wire JSON fields | direct controller-bean consumers need recompile; HTTP clients keep the same response JSON |
| `service_version` / `image` column naming | physical column names effectively followed the active JPA naming strategy | table and column names are now fixed with explicit JPA mappings | custom naming strategies that expected different physical names must align schema or mappings before upgrade |

## What Did Not Change

These remain stable in the current draft:

- oauth redirect endpoint property names
- callback endpoint shapes
- `relayCode` flow itself
- `atomic.app.version` HTTP contract
- `atomic.app.image` endpoint path and response envelope in this workstream

## Detailed Changes

### 1. Query Callback State Is Now One-Time

#### Before

- Google/Kakao callback paths verified callback state without consuming it.
- The same signed state could be accepted more than once depending on deployment and store setup.

#### Now

- Google/Kakao callback paths use one-time verification semantics.
- Reusing the same callback `state` is rejected.

#### What You Need To Do

- Do not rely on retrying the same browser callback URL after it has already succeeded once.
- If your frontend retries callback handling, restart from the redirect endpoint instead of replaying the old callback URL.

### 2. Callback-Binding Cookie Is Cleared After Success

#### Before

- callback-binding cookie could remain until expiry and be reused across flows

#### Now

- successful callback clears the callback-binding cookie immediately

#### What You Need To Do

- Treat callback-binding cookie as a single redirect-to-callback continuity token.
- If a user starts a new login attempt, send them through the redirect endpoint again.
- If you had custom browser automation or QA scripts assuming the cookie survives success, update them.

### 3. `enabled=true` Now Means Fail-Fast

#### Before

- `atomic.app.oauth.redirect.enabled=true` did not always mean the redirect/callback endpoints would actually be available.
- Missing oauth prerequisites could result in the feature being partially absent.

#### Now

- startup fails unless both of these are present:
  - `OauthServiceProvider`
  - store-backed `OauthStateManager`

#### What You Need To Do

- If you enable app oauth redirect, ensure your oauth provider module is configured and loaded.
- Do not assume `enabled=true` is enough by itself.

### 4. Store-Backed `OauthStateManager` Is Required

#### Before

- `OauthStateManager` could exist without replay protection backing store

#### Now

- oauth redirect requires replay-protected state handling
- the easiest built-in single-node setup is:

```yaml
atomic:
  oauth2:
    state:
      signing-secret: CHANGE_ME_WITH_STRONG_RANDOM_STATE_SECRET_AT_LEAST_32_BYTES
      in-memory-store:
        enabled: true
```

#### What You Need To Do

- Single-node/dev:
  - enable `atomic.oauth2.state.in-memory-store.enabled=true`
- Multi-instance/prod:
  - provide a shared/custom `OauthStateStore`
- If you only configured `signing-secret` before, that is no longer enough for app oauth redirect.

### 5. `allowed-redirect-uri-prefixes` Validation Moved To Startup

#### Before

- malformed allowlist entries could survive boot and fail at request time

#### Now

- startup fails if any configured allowlist entry is invalid

Valid entries must be:

- absolute URIs
- without user-info
- without query string
- without fragment

Examples:

- valid: `https://app.example.com/oauth`
- valid: `https://admin.example.com/login/callback`
- invalid: `https://app.example.com/oauth?env=dev`
- invalid: `https://user@app.example.com/oauth`
- invalid: `/oauth/callback`

### 6. Cache Relay Store Now Requires Atomic Consume Support

#### Before

- cache relay consume used a read-then-evict path
- that path depended on backend behavior and could not guarantee one-time consume under concurrency

#### Now

- cache relay consume requires an atomic remove-and-return path
- supported examples in the current implementation are native `ConcurrentMap.remove`, native `getAndRemove(...)`, and cache-native `asMap().remove(...)`
- unsupported cache backends cause startup failure by default
- if `atomic.app.oauth.redirect.store.fail-fast=false`, unsupported cache backends fall back to the in-memory relay store instead

#### What You Need To Do

- if you use `atomic.app.oauth.redirect.store.type=cache`, verify that your selected cache backend exposes one of the supported atomic consume paths
- if you run multi-instance production, do not rely on `store.fail-fast=false` fallback because the fallback store is process-local
- re-test duplicate relay consume behavior when changing cache provider or cache abstraction

### 7. App Modules Now Ship Built-In `HttpStatusException` Mapping

#### Before

- app module services/controllers could throw `HttpStatusException`
- to guarantee the documented `400/403/404` wire response, many host apps still needed their own exception advice

#### Now

- `atomic.app.version`, `atomic.app.image`, and `atomic.app.oauth.redirect` register controller-specific `HttpStatusException` mapping by default
- the documented HTTP status and `BaseResponse.error(...)` envelope now work without extra host-app advice

#### What You Need To Do

- if you were missing exception advice before, re-test and confirm the built-in mapping now matches your expected wire contract
- if your app already has custom global/controller advice, verify precedence and final envelope shape
- if you intentionally want a different envelope for app-module controllers, use a higher-precedence advice

### 8. Image Delete No Longer Guesses Storage Backend From Path

#### Before

- delete could fall back from persisted `ImageEntity.storageType` to path-based resolution using `{service}` / `{storageService}`
- a stale or missing stored mapping could still delete from a currently configured backend if the path-based guess matched

#### Now

- delete uses the persisted `ImageEntity.storageType` only
- if that stored mapping is unavailable, delete fails with `400`
- storage objects and metadata are left untouched when this happens

#### What You Need To Do

- keep configured storage client keys stable for already-uploaded images
- if you rename storage keys, migrate existing `image.storage_type` values before relying on delete
- re-test delete flows after changing storage backend naming conventions

### 9. Image Delete Now Uses `DELETE_PENDING` As Retryable State

#### Before

- delete tried to remove storage objects and metadata in the same request path
- partial failures were harder to reason about operationally

#### Now

- delete first reserves the row as `DELETE_PENDING`
- storage delete runs after reservation
- metadata is purged only after storage delete succeeds
- if storage delete fails, the row remains `DELETE_PENDING` and a later delete can retry cleanup

#### What You Need To Do

- treat lingering `DELETE_PENDING` rows as retryable cleanup work, not as successful deletes
- re-run delete after the storage/backend problem is fixed
- if you want operator-driven cleanup without replaying the original HTTP delete call, use `AppImageDeleteRecoveryService.recoverDeletePendingImages(limit)` from your own admin job or scheduler; the library intentionally does not ship a built-in reaper
- if you have admin tooling or dashboards that assumed only `ACTIVE`, include `DELETE_PENDING`

### 10. `service_version` And `image` Physical Names Are Now Fixed

#### Before

- these tables effectively followed your active JPA physical naming strategy
- most Spring Boot defaults still produced the shipped PostgreSQL names, but this was implicit

#### Now

- `service_version` and `image` use explicit `@Table` / `@Column` mappings
- shipped SQL assets and JPA mappings now agree on the same physical names

#### What You Need To Do

- if you already used the shipped/default PostgreSQL names, no action is needed
- if your deployment depended on a custom naming strategy that produced different names, align the schema before upgrade
- review any custom SQL, BI queries, or migration tools that assumed alternate physical names

## Recommended Migration Checklist

1. Check whether you use `atomic.app.oauth.redirect.enabled=true`.
2. If yes, confirm you have both `OauthServiceProvider` and store-backed `OauthStateManager`.
3. Review `allowed-redirect-uri-prefixes` and remove any query/fragment/user-info entries.
4. Re-test app module `400/403/404` responses if you previously relied on host-app exception advice.
5. Re-test browser login flow with callback-binding enabled.
6. Re-test repeated callback URL access and confirm it is rejected.
7. Re-test multi-tab login behavior if your product depends on it.
8. Re-test image delete after any storage client key rename or consolidation.
9. Check whether any operational tooling needs to recognize `DELETE_PENDING`.
10. If you use custom JPA naming strategies for `service_version` or `image`, verify that your physical schema still matches the now-explicit mappings.

## Validation Checklist

After migration, validate at least these:

- `GET /oauth/redirect/{provider}?redirectUri=...` still redirects correctly
- successful callback redirects frontend with `relayCode`
- replaying the same callback `state` fails
- successful callback clears callback-binding cookie
- app fails startup when oauth redirect is enabled but state store/provider wiring is incomplete
- app module `HttpStatusException` responses return documented statuses without extra host-app advice
- image delete fails safely when persisted `storageType` no longer matches configured storage client keys
- image delete leaves `DELETE_PENDING` when storage cleanup fails and succeeds on retry after recovery
- `service_version` and `image` tables match the explicit shipped SQL/JPA physical names
