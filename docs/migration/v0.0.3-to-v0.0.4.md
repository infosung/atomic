# Release Migration Guide: `v0.0.3` -> `v0.0.4`

> This document is the release-scoped source of truth for upgrade impact into `v0.0.4`.

## Who Should Read This

Read this guide if you use any of these:

- `atomic.app`
- `atomic-app:app-version`
- `atomic-app:storage-api`
- `atomic-app:oauth-redirect`
- `atomic-storage`
- `atomic-spring-oauth2`

If you use only these modules, this release does not currently require a dedicated migration item:

- `atomic.contract`
- `atomic.spring.web`
- `atomic.spring.security`
- `atomic.spring.idempotency`
- `atomic.heartbeat`

## Release Scope

`v0.0.4` is a topology-and-seam release. The main changes are source-level architecture cleanup, supported extension seam clarification, and migration notes for advanced adopters.

| Module / path | Release impact |
|---|---|
| `atomic-app:app-version` | legal-style package topology and supported host seam narrowed to `CheckAppVersionUseCase` |
| `atomic-app:oauth-redirect` | legal-style package topology, typed oauth state/id-token seams, explicit redirect/relay supported seams |
| `atomic-spring-oauth2` | duplicate provider fail-fast, typed state/id-token helpers, oauth exception boundary no longer inherits HTTP status |
| `atomic-app:storage-api` | legal-style package topology, use-case seams replace old concrete service seam |
| `atomic-storage` | advanced image strategy imports move from `image.*` to `image.spi.*` |

## Applicability Matrix

| Area | Main adopters affected | Change type | Required action |
|---|---|---|---|
| Version API host overrides | apps that customized `AppVersionCheckService` or other root support types | source-level seam | migrate to the exported `CheckAppVersionUseCase` bean and keep custom logic above the controller HTTP contract |
| OAuth redirect host overrides | apps that wired old root redirect/relay services directly | source-level seam | migrate to exported build/issue/consume use-case beans, `OauthRelayCodeStore`, and the web adapter beans |
| OAuth foundation exception mapping | apps that treated `HttpIOException` / `HttpJwtVerifyException` as `HttpStatusException` | behavior + source-level | catch them as oauth exceptions and map HTTP status only in adapter/web code |
| Storage API host overrides | apps that overrode `AppImageApiService` or delete-recovery concrete services | source-level seam | migrate to exported upload/delete/inspect/recover use-case beans and keep web overrides on the controller boundary |
| `atomic-storage` advanced image strategies | apps that imported strategy/helper types from `com.infosung.atomic.storage.image.*` | source-level import | update imports to `com.infosung.atomic.storage.image.spi.*` |

## Detailed Changes

### 1. `app-version` Now Uses Legal-Style Topology and a Narrower Host Seam

#### Before

- root package types such as `AppVersionCheckService` were the most visible customization path.
- controller, handler, persistence, and service concerns were not documented as a legal-style package boundary.

#### Now

- version API internals are organized under `application`, `domain`, `adapter`, and split auto-configuration packages.
- the supported host override seam is the exported `CheckAppVersionUseCase` bean.
- the controller HTTP contract remains the same (`400` / `404` semantics stay at the web boundary).

#### What You Need To Do

- if you previously overrode `AppVersionCheckService` or depended on old root support/composition types, migrate that customization to `CheckAppVersionUseCase`.
- keep custom controller/security behavior at the HTTP boundary; avoid depending on internal adapter/persistence support classes.
- no new schema change is introduced in this release. Existing `service_version` runtime/preflight requirements from `v0.0.3` still apply.

### 2. `oauth-redirect` Supported Seams Are Now Explicit

#### Before

- old root redirect/relay facade services were easier to discover than the underlying use-case seams.
- callback/state/id-token helpers still exposed more raw claim-key and HTTP-oriented behavior than intended.

#### Now

- supported host seams are:
  - exported build/issue/consume use-case beans
  - exported `OauthRelayCodeStore`
  - exported web adapter beans `AppOauthRedirectController` / `AppOauthRedirectHttpExceptionHandler`
- typed state/id-token helpers are available and documented as the preferred path for new integrations.
- oauth remote/provider failures are translated to `400` / `500` only at the app/web adapter boundary.

#### What You Need To Do

- if you referenced old root facade/service FQCNs directly, migrate to the documented use-case/store/web-adapter seams.
- if you read state or id-token claims manually from `Jwt.claims`, prefer `readStateClaims(...)`, `verifyStateClaims(...)`, and `verifyIdTokenClaims(...)`.
- if you mapped oauth exceptions directly to HTTP in lower layers, move that mapping into your adapter/web layer.

### 3. `atomic-spring-oauth2` No Longer Treats Core OAuth Failures as HTTP Exceptions

#### Before

- `HttpIOException` and `HttpJwtVerifyException` carried `HttpStatusException` semantics, which made lower-layer oauth failures look transport-specific.

#### Now

- those types remain named oauth exceptions, but they no longer inherit `HttpStatusException`.
- web/application adapters decide whether they should become `400`, `500`, or non-HTTP failures.
- `OauthServiceProvider` also fails fast when duplicate `OauthProviderName` registrations exist.

#### What You Need To Do

- if you were catching `HttpStatusException` to detect oauth foundation failures, update that code to catch the oauth exceptions directly.
- keep HTTP status mapping at controller/web-adapter level.
- if you intentionally register multiple providers, make sure each `OauthProviderName` is unique at startup.

### 4. `storage-api` Promotes Use-Case Seams Instead of Concrete Service Overrides

#### Before

- concrete service types such as `AppImageApiService` were easier to treat as override seams even though they were implementation details.

#### Now

- supported Spring seams are the exported use-case beans:
  - `UploadAppImageUseCase`
  - `DeleteAppImageUseCase`
  - `InspectDeletePendingImagesUseCase`
  - `RecoverDeletePendingImagesUseCase`
- auto-configuration keeps concrete storage-api services hidden behind internal shared operations.
- controller/wire contract remains stable.

#### What You Need To Do

- if your host app overrode or injected `AppImageApiService` or `AppImageDeleteRecoveryService`, migrate that customization to the exported use-case beans instead.
- keep custom web behavior at the controller boundary.
- no new image schema change is introduced in this release. Existing `v0.0.3` image/delete-recovery schema requirements still apply.

### 5. `atomic-storage` Advanced Image Strategy Imports Move to `.image.spi`

#### Before

- advanced strategy/helper types lived under `com.infosung.atomic.storage.image.*`.

#### Now

- the advanced image customization seam lives under `com.infosung.atomic.storage.image.spi.*`.
- `ImageService` remains the compatibility-stable facade for upload/delete orchestration.

#### What You Need To Do

- update imports for advanced customization types:

| Old import | New import |
|---|---|
| `com.infosung.atomic.storage.image.ImageObjectKeyGenerator` | `com.infosung.atomic.storage.image.spi.ImageObjectKeyGenerator` |
| `com.infosung.atomic.storage.image.ImageInputValidator` | `com.infosung.atomic.storage.image.spi.ImageInputValidator` |
| `com.infosung.atomic.storage.image.ImageMetadataReader` | `com.infosung.atomic.storage.image.spi.ImageMetadataReader` |
| `com.infosung.atomic.storage.image.ImageThumbnailGenerator` | `com.infosung.atomic.storage.image.spi.ImageThumbnailGenerator` |
| `com.infosung.atomic.storage.image.DefaultImageObjectKeyGenerator` | `com.infosung.atomic.storage.image.spi.DefaultImageObjectKeyGenerator` |
| `com.infosung.atomic.storage.image.CommonsImagingImageInputValidator` | `com.infosung.atomic.storage.image.spi.CommonsImagingImageInputValidator` |
| `com.infosung.atomic.storage.image.CommonsImagingMetadataReader` | `com.infosung.atomic.storage.image.spi.CommonsImagingMetadataReader` |
| `com.infosung.atomic.storage.image.DefaultImageThumbnailGenerator` | `com.infosung.atomic.storage.image.spi.DefaultImageThumbnailGenerator` |

- if you only use `ImageService` without overriding these strategy seams, no source change is required.

## Release Validation Checklist

- update dependency coordinates to `0.0.4`
- run `./gradlew spotlessCheck test` against your own integration matrix
- if you customize app-version behavior, verify your override now hangs from `CheckAppVersionUseCase`
- if you customize oauth redirect behavior, verify your overrides target the documented use-case/store/web-adapter seams
- if you customize oauth foundation error handling, confirm you no longer rely on `HttpStatusException` inheritance from `HttpIOException` / `HttpJwtVerifyException`
- if you customize `atomic-storage` image strategy helpers, update imports to `.image.spi.*`
