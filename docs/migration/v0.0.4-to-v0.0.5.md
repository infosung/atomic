# Release Migration Guide: `v0.0.4` -> `v0.0.5`

> Draft release-scoped guide for the public error seam redesign in `v0.0.5`.

## Who Should Read This

Read this guide if you use any of these:

- `atomic-app:app-version`
- `atomic-app:oauth-redirect`
- `atomic-app:storage-api`
- `atomic-spring-security`
- `atomic-spring-idempotency`
- `atomic-spring-web`
- `atomic.contract`

## Release Scope

`v0.0.5` is an exception-contract release. The goal is to stop host applications from depending on internal exception FQCNs or message text when they customize error handling.

| Area | Release impact |
|---|---|
| `atomic.contract` | `HttpStatusException` grows a stable wire `code` contract instead of relying on exception simple name only |
| `atomic-spring-web` | shared global `HttpStatusException` / fallback exception handling becomes the default app-level mapping path |
| `atomic-spring-security` | security rejection paths expose stable non-MVC codes |
| `atomic-spring-idempotency` | idempotency rejection paths expose stable non-MVC codes |
| `atomic-app:app-version` | public version exceptions become the supported host seam; module-local HTTP handler is removed |
| `atomic-app:oauth-redirect` | public oauth redirect / relay exceptions become the supported host seam; module-local HTTP handler is removed |
| `atomic-app:storage-api` | public storage exceptions remain supported; module-local HTTP handler is removed in favor of shared web mapping |

## Applicability Matrix

| Area | Main adopters affected | Change type | Required action |
|---|---|---|---|
| Host apps with custom version error handling | apps like `newserver` that matched atomic messages / FQCNs | source + behavior | migrate to typed public exceptions or stable `HttpStatusException.code` |
| Apps relying on built-in module-local advice beans | apps that referenced `AppVersionHttpExceptionHandler`, `AppOauthRedirectHttpExceptionHandler`, or `AppStorageHttpExceptionHandler` directly | source-level | migrate to shared `atomic-spring-web` exception mapping or your own global `@RestControllerAdvice` |
| Apps that expose app-module endpoints without any global web exception policy | behavior | ensure `atomic-spring-web` shared handler is active, or register an equivalent host handler |
| Hosts that issue their own response envelope | behavior | map from stable `HttpStatusException.code` or module public exceptions instead of parsing prose messages |
| Apps that assumed plain text filter rejection bodies | behavior | read JSON `BaseResponse.code/message` for `security`, `rate-limit`, and `idempotency` rejection paths |

## Error Contract Direction

### Before

- most app-module HTTP errors serialized as:
  - `code = "HttpStatusException"`
  - `message = <message text>`
- host apps often had to recover meaning from:
  - internal exception FQCN strings
  - literal message text

### Now

- app modules publish stable error identity through:
  - public module exception types for direct host/use-case integration
  - stable `HttpStatusException.code` values for web responses
- shared web handling is centralized through `atomic-spring-web`
- the built-in shared handler is scoped to `atomic.app.*` controllers
- host apps can still provide one global `BaseExceptionHandler` subclass for broader policy
- if a host wants to suppress the built-in scoped handler entirely, its advice must explicitly implement `AtomicHttpExceptionHandlerReplacement`
- do not rely on plain advice ordering to replace the built-in scoped handler; when multiple matching advice handlers coexist, Spring advice ordering determines which one runs
- host-managed `BaseExceptionHandler` subclasses now own their own alert policy directly; the built-in handler still emits no alerts because it disables alert delivery through `shouldAlert(...) = false`
- `BaseExceptionHandler` now exposes narrow customization hooks:
  - `shouldAlert(...)` to suppress or narrow alert delivery without replacing the handler methods
  - `createErrorResponse(...)` to customize the response envelope without reimplementing every exception handler method
- module-local `*HttpExceptionHandler` classes are no longer the supported extension seam

## Module Notes

### 1. `app-version`

Expected stable wire catalog:

| Code | Status | Default message |
|---|---:|---|
| `VERSION_SERVICE_NAME_REQUIRED` | `400` | `Service name is required.` |
| `VERSION_PLATFORM_REQUIRED` | `400` | `Platform is required.` |
| `VERSION_APP_VERSION_REQUIRED` | `400` | `App version is required.` |
| `VERSION_INVALID_APP_VERSION` | `400` | `App version is invalid.` |
| `VERSION_POLICY_NOT_FOUND` | `404` | `No version policy was found.` |

Host apps should stop matching:

- `InvalidAppVersionException` FQCN string
- `VersionPolicyNotFoundException` FQCN string
- version error message text

Instead, prefer:

- catching the public version exception types when calling the use case directly
- mapping on `HttpStatusException.code` at the HTTP boundary

### 2. `oauth-redirect`

Supported host-facing failures are now exposed through public exception types plus stable
`errorCode` values for:

- unsupported provider
- invalid redirect URI / invalid request
- callback binding / state validation failures
- relay code invalid / expired / already consumed
- upstream oauth provider failure

Expected stable wire catalog:

| Code | Status | Default message |
|---|---:|---|
| `OAUTH_REDIRECT_INVALID_REQUEST` | `400` | `OAuth redirect request is invalid.` |
| `OAUTH_CALLBACK_INVALID_REQUEST` | `400` | `OAuth callback request is invalid.` |
| `OAUTH_PROVIDER_UNSUPPORTED` | `400` | `OAuth provider is not supported.` |
| `OAUTH_REDIRECT_URI_INVALID` | `400` | `OAuth redirect URI is invalid.` |
| `OAUTH_CALLBACK_BINDING_INVALID` | `400` | `OAuth callback binding is invalid.` |
| `OAUTH_STATE_INVALID` | `400` | `OAuth callback state is invalid.` |
| `OAUTH_PROVIDER_REMOTE_FAILURE` | `500` | `Upstream OAuth provider request failed.` |
| `OAUTH_APPLE_CALLBACK_POST_ONLY` | `400` | `Apple callback supports POST form_post only.` |
| `OAUTH_REDIRECT_CONFIGURATION_INVALID` | `500` | `OAuth redirect configuration is invalid.` |
| `OAUTH_RELAY_CODE_REQUIRED` | `400` | `OAuth relay code is required.` |
| `OAUTH_RELAY_CODE_INVALID_REQUEST` | `400` | `OAuth relay code request is invalid.` |

Additional refinements in this phase:

- unsupported provider is now split out as `OAUTH_PROVIDER_UNSUPPORTED`
- invalid or disallowed redirect URI is now split out as `OAUTH_REDIRECT_URI_INVALID`
- callback binding cookie/token mismatches are now split out as `OAUTH_CALLBACK_BINDING_INVALID`
- invalid or expired oauth state is now split out as `OAUTH_STATE_INVALID`
- blank relay code is now split out as `OAUTH_RELAY_CODE_REQUIRED`
- `5xx` oauth codes keep stable `code`/`status`, but the built-in shared handler still masks the default wire message to `Internal Server Error` unless a host replaces that behavior

### 3. `storage-api`

Storage application exceptions were already public in `v0.0.4`; `v0.0.5` aligns the web contract with the same public seam.

Expected stable wire catalog:

| Code | Status | Default message |
|---|---:|---|
| `STORAGE_INVALID_IMAGE_REQUEST` | `400` | `Storage image request is invalid.` |
| `STORAGE_IMAGE_QUALITY_INVALID` | `400` | `Storage image quality is invalid.` |
| `STORAGE_FILE_NAME_REQUIRED` | `400` | `Storage image file name is required.` |
| `STORAGE_IMAGE_ID_INVALID` | `400` | `Storage imageId is invalid.` |
| `STORAGE_IMAGE_PATH_MISMATCH` | `400` | `Storage image does not match request path.` |
| `STORAGE_STORAGE_TYPE_UNAVAILABLE` | `400` | `Stored storage type is unavailable.` |
| `STORAGE_IMAGE_NOT_FOUND` | `404` | `Storage image was not found.` |
| `STORAGE_IMAGE_OWNERSHIP_MISMATCH` | `403` | `Storage image ownership does not match.` |
| `STORAGE_UPLOADER_PARAMETER_REQUIRED` | `400` | `Uploader parameter is required.` |
| `STORAGE_CONFIGURATION_INVALID` | `500` | `Storage configuration is invalid.` |

Additional refinements in this phase:

- invalid upload quality is now split out as `STORAGE_IMAGE_QUALITY_INVALID`
- missing original filename is now split out as `STORAGE_FILE_NAME_REQUIRED`
- invalid delete `imageId` format is now split out as `STORAGE_IMAGE_ID_INVALID`
- delete path `service/storageService` mismatch is now split out as `STORAGE_IMAGE_PATH_MISMATCH`
- persisted delete storage type no longer configured is now split out as `STORAGE_STORAGE_TYPE_UNAVAILABLE`
- blank uploader tracking configuration now consistently maps to `STORAGE_CONFIGURATION_INVALID`
- storage `5xx` codes keep stable `code`/`status`, but the built-in shared handler still masks the default wire message to `Internal Server Error` unless a host replaces that behavior

### 4. Non-MVC platform filters

Expected stable codes now also cover non-MVC rejection paths:

| Area | Code | Status | Default message |
|---|---|---:|---|
| security | `SECURITY_UNAUTHORIZED` | `401` | `Unauthorized` |
| security | `SECURITY_FORBIDDEN` | `403` | `Forbidden` |
| rate-limit | `RATE_LIMIT_KEY_REQUIRED` | `400` | `Rate-limit key is missing.` |
| rate-limit | `RATE_LIMIT_EXCEEDED` | `429` | `Too many requests.` |
| idempotency | `IDEMPOTENCY_KEY_REQUIRED` | `400` | `Idempotency-Key header is required.` |
| idempotency | `IDEMPOTENCY_REQUEST_PROCESSING` | `409` | `Idempotent request is already processing.` |
| idempotency | `IDEMPOTENCY_FINGERPRINT_MISMATCH` | `409` | `Idempotency key has been used with a different request.` |

Those rejection paths now return JSON `BaseResponse` payloads instead of generic/plain text-only
error bodies.

This release does not introduce a stable Atomic `500` envelope for unexpected non-MVC filter faults.
Expected rejection branches are standardized; unexpected infrastructure/runtime faults remain
implementor-owned. If your service needs uniform `500` handling there, add host-specific outer
filter/container/global error handling and explicitly cover resolver/store/serialization failures.

## Migration Checklist

- Replace message/FQCN matching with:
  - public atomic module exception types, or
  - `HttpStatusException.code`
- Remove direct dependency on:
  - `AppVersionHttpExceptionHandler`
  - `AppOauthRedirectHttpExceptionHandler`
  - `AppStorageHttpExceptionHandler`
- Ensure your app has one global exception policy for `HttpStatusException`
- Re-test:
  - `400` request validation branches
  - `404` not-found / missing-policy branches
  - oauth upstream failure branches
  - storage ownership / delete-pending error branches
  - security unauthorized / forbidden branches
  - rate-limit missing-key and throttle branches
  - idempotency missing-header and conflict branches
