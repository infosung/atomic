# Release Migration Guide: `v0.0.4` -> `v0.0.5`

> Draft release-scoped guide for the public error seam redesign in `v0.0.5`.

## Who Should Read This

Read this guide if you use any of these:

- `atomic-app:app-version`
- `atomic-app:oauth-redirect`
- `atomic-app:storage-api`
- `atomic-spring-web`
- `atomic.contract`

## Release Scope

`v0.0.5` is an exception-contract release. The goal is to stop host applications from depending on internal exception FQCNs or message text when they customize error handling.

| Area | Release impact |
|---|---|
| `atomic.contract` | `HttpStatusException` grows a stable wire `code` contract instead of relying on exception simple name only |
| `atomic-spring-web` | shared global `HttpStatusException` / fallback exception handling becomes the default app-level mapping path |
| `atomic-app:app-version` | public version exceptions become the supported host seam; module-local HTTP handler is removed |
| `atomic-app:oauth-redirect` | public oauth redirect / relay exceptions become the supported host seam; module-local HTTP handler is removed |
| `atomic-app:storage-api` | public storage exceptions remain supported; module-local HTTP handler is removed in favor of shared web mapping |

## Applicability Matrix

| Area | Main adopters affected | Change type | Required action |
|---|---|---|---|
| Host apps with custom version error handling | apps like `newserver` that matched atomic messages / FQCNs | source + behavior | migrate to typed public exceptions or stable `HttpStatusException.code` |
| Apps relying on built-in module-local advice beans | apps that referenced `AppVersionHttpExceptionHandler`, `AppOauthRedirectHttpExceptionHandler`, or `AppStorageHttpExceptionHandler` directly | source-level | migrate to shared `atomic-spring-web` exception mapping or your own global `@RestControllerAdvice` |
| Apps that expose app-module endpoints without any global web exception policy | behavior | ensure `atomic-spring-web` shared handler is active, or register an equivalent host handler |
| Hosts that issue their own response envelope | behavior | map from stable `HttpStatusException.code` or module public exceptions instead of parsing prose messages |

## Error Contract Direction

### Before

- most app-module HTTP errors serialized as:
  - `code = "HttpStatusException"`
  - `message = <message text>`
- host apps often had to recover meaning from:
  - internal exception FQCN strings
  - literal message text

### Now

- app modules publish stable error identity through:
  - public module exception types for direct host/use-case integration
  - stable `HttpStatusException.code` values for web responses
- shared web handling is centralized through `atomic-spring-web`
- module-local `*HttpExceptionHandler` classes are no longer the supported extension seam

## Module Notes

### 1. `app-version`

Expected stable wire codes:

- `VERSION_SERVICE_NAME_REQUIRED`
- `VERSION_PLATFORM_REQUIRED`
- `VERSION_APP_VERSION_REQUIRED`
- `VERSION_INVALID_APP_VERSION`
- `VERSION_POLICY_NOT_FOUND`

Host apps should stop matching:

- `InvalidAppVersionException` FQCN string
- `VersionPolicyNotFoundException` FQCN string
- version error message text

Instead, prefer:

- catching the public version exception types when calling the use case directly
- mapping on `HttpStatusException.code` at the HTTP boundary

### 2. `oauth-redirect`

Supported host-facing failures are now typed and public for:

- unsupported provider
- invalid redirect URI / invalid request
- callback binding / state validation failures
- relay code invalid / expired / already consumed
- upstream oauth provider failure

Expected stable wire codes are module-specific oauth redirect codes rather than plain `HttpStatusException`.

### 3. `storage-api`

Storage application exceptions were already public in `v0.0.4`; `v0.0.5` aligns the web contract with the same public seam.

Expected stable wire codes use storage-specific values rather than generic `HttpStatusException`.

## Migration Checklist

- Replace message/FQCN matching with:
  - public atomic module exception types, or
  - `HttpStatusException.code`
- Remove direct dependency on:
  - `AppVersionHttpExceptionHandler`
  - `AppOauthRedirectHttpExceptionHandler`
  - `AppStorageHttpExceptionHandler`
- Ensure your app has one global exception policy for `HttpStatusException`
- Re-test:
  - `400` request validation branches
  - `404` not-found / missing-policy branches
  - oauth upstream failure branches
  - storage ownership / delete-pending error branches
