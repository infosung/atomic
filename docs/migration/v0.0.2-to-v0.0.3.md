# Release Migration Guide: `v0.0.2` -> `v0.0.3`

> This document is the release-scoped source of truth for upgrade impact into `v0.0.3`.

## Who Should Read This

Read this guide if you use any of these:

- `atomic.app`
- `atomic-app:app-version`
- `atomic-app:storage-api`
- `atomic-app:oauth-redirect`
- `atomic-storage`
- `atomic-spring-web` request-language helper consumers

If you use only these modules, this release does not currently require a dedicated migration item:

- `atomic.spring.security`
- `atomic.spring.idempotency`
- `atomic.heartbeat`

## Release Scope

`v0.0.3` is a hardening release. The largest changes are:

| Module / path | Release impact |
|---|---|
| `atomic-spring-web` | source-level helper addition |
| `atomic-app:app-version` | schema preflight hardening |
| `atomic-app:storage-api` | schema hardening, delete recovery workflow, operational logging |
| `atomic-storage` | input/object-key/public-url budget hardening |
| `atomic-app:oauth-redirect` | startup summary, deep-link contract clarification |

## Applicability Matrix

| Area | Main adopters affected | Change type | Required action |
|---|---|---|---|
| Request language helper | services parsing `X-Custom-Language` / `Accept-Language` manually | source behavior | prefer the shared helper if you want canonicalized request language hints |
| `service_version` startup preflight | `atomic-app:app-version` schema owners | schema + configuration | ensure runtime-required columns still exist before rolling out `v0.0.3` |
| `image` widened externally sized columns | `storage-api` schema owners | schema | widen existing `VARCHAR(255)` columns before rollout |
| `DELETE_PENDING` recovery claims | `storage-api` operators | behavior + operational | update custom image schema and retry tooling to include claim columns/index |
| image upload input budgets | `atomic-storage` / `storage-api` users | behavior | treat over-budget object key / public URL values as pre-write failures |
| oauth redirect deployment summary | `atomic-app:oauth-redirect` users | operational | review startup logs and ensure chosen store/topology combination matches deployment |

## Detailed Changes

### 1. Shared Request Language Hint Extraction Exists Now

#### Before

- host services often re-parsed `X-Custom-Language` and `Accept-Language` manually.

#### Now

- `atomic-spring-web` exposes a shared request language helper.
- it prefers `X-Custom-Language`.
- otherwise it falls back to the servlet-preferred locale and returns a canonicalized language tag.

#### What You Need To Do

- if your service already has a custom header parser, decide whether to keep domain-specific logic or adopt the shared helper.
- do not treat this helper as full locale negotiation; supported-locale selection remains caller-owned.

### 2. `service_version` Preflight Covers Actual Runtime Contract

#### Before

- startup width checks focused on `store_url`.
- some runtime schema gaps could still survive until the first real request path.

#### Now

- app-version startup preflight also validates the required runtime column contract, including `store_available`.
- startup fails earlier when the table shape is no longer compatible.
- the shipped baseline remains `TEXT` for `store_url`, but custom schemas are still accepted when they use a sufficiently wide `VARCHAR(>=1024)` equivalent.

#### What You Need To Do

- if you own custom `service_version` migrations, verify the table still includes the shipped runtime columns.
- if you own custom `service_version` migrations, also keep the shipped supporting indexes, especially `idx_service_version_service_platform_required_update`, so required-update lookups retain the tested access path.
- treat preflight failures as schema blockers, not transient API errors.

Minimum shipped runtime columns include:

- `id`
- `service`
- `platform`
- `main_version`
- `minor_version`
- `patch_number`
- `require_update`
- `store_available`
- `store_url`
- `created_at`

The shipped PostgreSQL asset and preflight contract are:

- `atomic-app/version/src/main/resources/META-INF/atomic/sql/postgresql/service_version.sql`
- `atomic-app/version/src/main/kotlin/com/infosung/atomic/app/version/autoconfigure/ServiceVersionSchemaPreflightContract.kt`

### 3. `image` Externally Sized Columns Must Be Widened

#### Before

- older installations could keep `VARCHAR(255)` for externally sized values such as object keys and public URLs.

#### Now

- shipped PostgreSQL assets use `TEXT` for:
  - `file_name`
  - `thumbnail_file_name`
  - `url`
  - `thumbnail_url`
- startup preflight rejects older narrow image schemas when the image API is enabled.

#### What You Need To Do

- widen old schemas before rollout.
- if you own custom SQL migrations, prefer explicit `ALTER TABLE ... TYPE TEXT`, or keep an equivalent `VARCHAR(>=1024)` shape if that is already your migration policy.

PostgreSQL baseline snippet:

```sql
ALTER TABLE service_version
  ALTER COLUMN store_url TYPE TEXT;

ALTER TABLE image
  ALTER COLUMN file_name TYPE TEXT,
  ALTER COLUMN thumbnail_file_name TYPE TEXT,
  ALTER COLUMN url TYPE TEXT,
  ALTER COLUMN thumbnail_url TYPE TEXT;
```

### 4. Delete Recovery Uses Claims To Avoid Overlapping Batches

#### Before

- overlapping recovery runs could inspect the same `DELETE_PENDING` rows.

#### Now

- recovery batches claim rows first.
- claimed rows can be reclaimed after the stale timeout (`15` minutes / `900` seconds).
- image schema now expects:
  - `delete_recovery_claim_token`
  - `delete_recovery_claimed_at`
  - `idx_image_status_claim_created_at`
- shipped SQL also includes `idx_image_status_created_at` for pending snapshot access paths.

#### What You Need To Do

- update custom image schema if you do not use the shipped SQL asset.
- if you keep custom image SQL, add both `idx_image_status_claim_created_at` and `idx_image_status_created_at` so recovery claim and inspection queries retain the shipped access path.
- keep host-owned recovery, but assume claimed rows may stay reserved briefly after interrupted runs.
- re-test admin retry/scheduler flows if you built them on top of the exported delete-recovery use-case seams.

PostgreSQL baseline snippet:

```sql
ALTER TABLE image
  ADD COLUMN IF NOT EXISTS delete_recovery_claim_token VARCHAR(255) NULL,
  ADD COLUMN IF NOT EXISTS delete_recovery_claimed_at TIMESTAMP WITHOUT TIME ZONE NULL;

CREATE INDEX IF NOT EXISTS idx_image_status_claim_created_at
  ON image (status, delete_recovery_claim_token, created_at);

CREATE INDEX IF NOT EXISTS idx_image_status_created_at
  ON image (status, created_at);
```

### 5. Image Upload Path Now Has Built-In Input Budgets

#### Before

- long filenames, generated object keys, and public URLs could grow without a caller-visible budget until later failures.

#### Now

- original object key and public URL are budget-checked before the storage write.
- generated object keys are bounded.
- thumbnail-only budget issues degrade into `thumbnailUploadFailed=true` instead of failing the original upload.
- logs now emit preview + length instead of the full raw values.
- current built-in ceilings are:
  - original object key: `512`
  - public URL: `2048`
  - thumbnail failure reason: `160`

#### What You Need To Do

- if your app depended on extremely long object keys or CDN URLs, re-test with representative production data.
- keep multipart/body-size limits in the host app; these budgets do not replace request-size protection.
- if you alert on upload failures, include the current budget values above in your runbook so operators can distinguish input-budget failures from backend outages.

### 6. OAuth Redirect Startup Summary Is More Explicit

#### Before

- store/topology choices were present in properties but less obvious at startup.

#### Now

- startup logs summarize relay store shape, fail-fast policy, callback-binding mode, and state-store topology.
- docs now pin the custom deep-link URI shape more explicitly.

#### What You Need To Do

- review startup logs in each deployment mode.
- if you use mobile deep links, verify your exact allowed URI shape (`myapp://...` vs `myapp:/...`) still matches your frontend contract.

## Release Validation Checklist

- confirm dependency coordinates are updated to `0.0.3`
- run `./gradlew spotlessCheck test` against your own application integration matrix
- if `atomic.app.version.enabled=true`, verify `service_version` preflight passes on your real schema
- if `atomic.app.image.enabled=true`, verify the `image` schema is widened and includes claim columns/index
- re-test delete retry / recovery behavior around `DELETE_PENDING`
- re-test image uploads with long but realistic filenames / object keys / CDN URLs
- review oauth redirect startup summary and mobile deep-link allowlist behavior
