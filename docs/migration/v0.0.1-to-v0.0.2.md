# Release Migration Guide: `v0.0.1` -> `v0.0.2`

> This document is the release-scoped source of truth for upgrade impact into `v0.0.2`.

## Who Should Read This

Read this guide if you currently use any of these:

- `atomic.app`
- `atomic-app:app-version`
- `atomic-app:storage-api`
- `atomic-app:oauth-redirect`
- `atomic.starter` + `atomic.spring.oauth2` with app-level oauth redirect flow
- host apps that directly depend on app-controller/source signatures instead of only HTTP wire contracts

If you only use these lower-level modules, this release does not currently introduce a required
migration item from this workstream:

- `atomic.contract`
- `atomic.spring.web`
- `atomic.spring.security`
- `atomic.spring.idempotency`
- `atomic.heartbeat`

## Release Scope

`v0.0.2` changes are concentrated in the app modules:

| Module / path | Release impact |
|---|---|
| `atomic-app:oauth-redirect` | behavior, configuration, and operational changes |
| `atomic-app:storage-api` | behavior, source-compatibility, schema, and operational changes |
| `atomic-app:app-version` | schema and app-controller behavior changes |

## Compatibility Labels Used In This Guide

- `wire contract`: HTTP path, status code, parameter, or JSON envelope visible to remote clients
- `source compatibility`: direct code usage of public classes, methods, controller return types, or bean signatures
- `schema`: database table, column, or SQL-asset expectations
- `configuration`: required properties, startup validation, or dependency wiring
- `operational`: cleanup ownership, monitoring, retry path, or deployment-model decisions

## Quick Impact Summary

### If you use only `atomic-app:app-version`

- HTTP path, required headers, and response JSON stay the same.
- App-level `HttpStatusException` mapping is now built in.
- `service_version` physical table/column names are now explicit contracts.
- duplicate semantic-version rows are no longer a valid schema state.
- unregistered but semantically valid client versions no longer return `400`.
- `currentVersion` / `requiredUpdate` now prefer rows where `store_available=true`.

### If you use `atomic-app:storage-api`

- Upload/delete endpoints stay the same.
- HTTP JSON stays the same, but the controller/source type is now `ImageResponse`.
- Delete is stricter and safer:
  - it uses persisted `storageType` only
  - it leaves retryable `DELETE_PENDING` rows on storage-delete failure

### If you use `atomic-app:oauth-redirect`

- This release is migration-significant.
- Callback state is one-time.
- Startup is stricter.
- Callback-binding now has explicit policy modes.
- Relay-store semantics must match your deployment model.

## Detailed Changes

### 1. Query Callback State Is Now One-Time

#### Before

- Google/Kakao callback paths verified callback state without consuming it.
- The same signed state could be accepted more than once depending on deployment and store setup.

#### Now

- Google/Kakao callback paths use one-time verification semantics.
- Reusing the same callback `state` is rejected.

#### What You Need To Do

- Do not rely on retrying the same browser callback URL after it has already succeeded once.
- If your frontend retries callback handling, restart from the redirect endpoint instead of replaying
  the old callback URL.

### 2. Callback-Binding Now Has Explicit Policy Modes

#### Before

- callback-binding cookie could remain until expiry and be reused across flows
- callback-binding enablement was expressed mainly as `callback-binding.enabled=true|false`

#### Now

- default `strict` mode clears the callback-binding cookie immediately
- `relaxed` mode preserves the callback-binding cookie after success
- `disabled` mode turns callback binding off
- legacy `callback-binding.enabled=false` still works, but `callback-binding.mode` is now the
  clearer long-term control

#### What You Need To Do

- If you want the most conservative behavior, keep the default `strict` mode and treat the cookie as
  a single redirect-to-callback continuity token.
- If your UX depends on the cookie surviving success across multi-tab/back-navigation flows, set
  `atomic.app.oauth.redirect.callback-binding.mode=relaxed`.
- If you intentionally disable callback binding for local-only testing, prefer
  `atomic.app.oauth.redirect.callback-binding.mode=disabled`.

### 3. `enabled=true` Now Means Fail-Fast

#### Before

- `atomic.app.oauth.redirect.enabled=true` did not always mean the redirect/callback endpoints would
  actually be available.
- Missing oauth prerequisites could result in the feature being partially absent.

#### Now

- startup fails unless both of these are present:
  - `OauthServiceProvider`
  - store-backed `OauthStateManager`

#### What You Need To Do

- If you enable app oauth redirect, ensure your oauth provider module is configured and loaded.
- Do not assume `enabled=true` is enough by itself.

### 4. Store-Backed `OauthStateManager` Is Required

#### Before

- `OauthStateManager` could exist without replay protection backing store

#### Now

- oauth redirect requires replay-protected state handling
- the easiest built-in single-node setup is:

```yaml
atomic:
  oauth2:
    state:
      signing-secret: CHANGE_ME_WITH_STRONG_RANDOM_STATE_SECRET_AT_LEAST_32_BYTES
      in-memory-store:
        enabled: true
```

#### What You Need To Do

- Single-node/dev:
  - enable `atomic.oauth2.state.in-memory-store.enabled=true`
- Multi-instance/prod:
  - provide a shared/custom `OauthStateStore`
- If you only configured `signing-secret` before, that is no longer enough for app oauth redirect.

### 5. `allowed-redirect-uri-prefixes` Validation Moved To Startup

#### Before

- malformed allowlist entries could survive boot and fail at request time

#### Now

- startup fails if any configured allowlist entry is invalid

Valid entries must be:

- absolute URIs
- without user-info
- without query string
- without fragment

Examples:

- valid: `https://app.example.com/oauth`
- valid: `https://admin.example.com/login/callback`
- invalid: `https://app.example.com/oauth?env=dev`
- invalid: `https://user@app.example.com/oauth`
- invalid: `/oauth/callback`

### 6. Cache Relay Store Now Requires Atomic Consume Support

#### Before

- cache relay consume used a read-then-evict path
- that path depended on backend behavior and could not guarantee one-time consume under concurrency

#### Now

- cache relay consume requires an atomic remove-and-return path
- unsupported cache backends cause startup failure by default
- if `atomic.app.oauth.redirect.store.fail-fast=false`, unsupported cache backends fall back to the
  in-memory relay store instead

#### What You Need To Do

- if you use `atomic.app.oauth.redirect.store.type=cache`, verify that your selected cache backend
  exposes the supported atomic consume path
- if you run multi-instance production, do not rely on `store.fail-fast=false` fallback because the
  fallback store is process-local
- re-test duplicate relay consume behavior when changing cache provider or cache abstraction

### 7. App Modules Now Ship Built-In `HttpStatusException` Mapping

#### Before

- app module services/controllers could throw `HttpStatusException`
- to guarantee the documented `400/403/404` wire response, many host apps still needed their own
  exception advice

#### Now

- `atomic.app.version`, `atomic.app.image`, and `atomic.app.oauth.redirect` register
  controller-specific `HttpStatusException` mapping by default
- the documented HTTP status and `BaseResponse.error(...)` envelope now work without extra host-app
  advice

#### What You Need To Do

- if you were missing exception advice before, re-test and confirm the built-in mapping now matches
  your expected wire contract
- if your app already has custom global/controller advice, verify precedence and final envelope
  shape
- if you intentionally want a different envelope for app-module controllers, use a
  higher-precedence advice

### 8. Image Delete No Longer Guesses Storage Backend From Path

#### Before

- delete could fall back from persisted `ImageEntity.storageType` to path-based resolution using
  `{service}` / `{storageService}`
- a stale or missing stored mapping could still delete from a currently configured backend if the
  path-based guess matched

#### Now

- delete uses the persisted `ImageEntity.storageType` only
- if that stored mapping is unavailable, delete fails with `400`
- storage objects and metadata are left untouched when this happens

#### What You Need To Do

- keep configured storage client keys stable for already-uploaded images
- if you rename storage keys, migrate existing `image.storage_type` values before relying on delete
- re-test delete flows after changing storage backend naming conventions

### 9. Image Delete Now Uses `DELETE_PENDING` As Retryable State

#### Before

- delete tried to remove storage objects and metadata in the same request path
- partial failures were harder to reason about operationally

#### Now

- delete first reserves the row as `DELETE_PENDING`
- storage delete runs after reservation
- metadata is purged only after storage delete succeeds
- if storage delete fails, the row remains `DELETE_PENDING` and a later delete can retry cleanup

#### What You Need To Do

- treat lingering `DELETE_PENDING` rows as retryable cleanup work, not as successful deletes
- re-run delete after the storage/backend problem is fixed
- if you want operator-driven cleanup without replaying the original HTTP delete call, use
  `AppImageDeleteRecoveryService.recoverDeletePendingImages(limit)` from your own admin job or
  scheduler; the library intentionally does not ship a built-in reaper
- if you have admin tooling or dashboards that assumed only `ACTIVE`, include `DELETE_PENDING`

### 10. `service_version` And `image` Physical Names Are Now Fixed

#### Before

- these tables effectively followed your active JPA physical naming strategy
- most Spring Boot defaults still produced the shipped PostgreSQL names, but this was implicit

#### Now

- `service_version` and `image` use explicit `@Table` / `@Column` mappings
- shipped SQL assets and JPA mappings now agree on the same physical names

#### What You Need To Do

- if you already used the shipped/default PostgreSQL names, no action is needed
- if your deployment depended on a custom naming strategy that produced different names, align the
  schema before upgrade
- review any custom SQL, BI queries, or migration tools that assumed alternate physical names

Pre-upgrade check (PostgreSQL example):

```sql
SELECT column_name
FROM information_schema.columns
WHERE table_name = 'service_version'
ORDER BY ordinal_position;

SELECT column_name
FROM information_schema.columns
WHERE table_name = 'image'
ORDER BY ordinal_position;
```

Expected names now include:

- `service_version`: `id`, `main_version`, `minor_version`, `patch_number`, `require_update`,
  `store_available`, `platform`, `service`, `store_url`, `created_at`
- `image`: `id`, `bucket`, `service_name`, `storage_service`, `status`, `uploader_id`,
  `storage_type`, `file_name`, `thumbnail_file_name`, `url`, `thumbnail_url`, `width`, `height`,
  `file_size`, `thumbnail_width`, `thumbnail_height`, `thumbnail_file_size`, `created_at`

`service_version` now also expects one semantic-version row only per:

- `service`
- `platform`
- `main_version`
- `minor_version`
- `patch_number`

### 11. Version Policy Resolution Is Now Rollout-Safe

#### Before

- a semantically valid client version still returned `400` when it did not exactly match a row in
  `service_version`
- future/review versions could accidentally become the apparent current version or forced-update
  target as soon as a row was inserted

#### Now

- semantically valid but unregistered client versions return `200`
- `requiredUpdate` only considers higher rows where `require_update=true` and `store_available=true`
- `currentVersion` prefers the latest `store_available=true` row
- `service_version.store_available` defaults to `TRUE`, so existing policy rows keep prior behavior
  until you opt into rollout-safe control

#### What You Need To Do

- stop depending on `400` as the signal for an unknown-but-valid client version
- remove duplicate `service_version` rows for the same semantic version before applying the official
  PostgreSQL asset in an existing environment
- use `store_available=false` for:
  - app-review builds
  - internal distribution rows
  - phased-rollout targets that are not yet safe for forced update
- flip `store_available=true` only when the version is safe to expose as the store target for all
  clients

### 12. Externally Sized Columns Now Require Widened Schema Before Startup

#### Before

- older installations could keep `VARCHAR(255)` for:
  - `service_version.store_url`
  - `image.file_name`
  - `image.thumbnail_file_name`
  - `image.url`
  - `image.thumbnail_url`
- application startup could still succeed, and the failure only appeared later when longer values
  were actually written

#### Now

- shipped PostgreSQL assets use `TEXT` for those columns
- if `atomic.app.version.enabled=true` or `atomic.app.image.enabled=true`, startup performs a schema
  upgrade preflight
- startup now fails fast when those columns are still too narrow
- custom schemas are accepted when they use a sufficiently wide equivalent such as `VARCHAR(1024+)`

#### What You Need To Do

- widen the affected columns before rolling out builds that include this preflight
- treat startup preflight errors as migration blockers, not as transient API errors
- if you own custom SQL migrations, prefer explicit `ALTER TABLE ... TYPE TEXT` for the shipped
  PostgreSQL baseline

## Release Validation Checklist

### Common

- confirm your runtime matches the documented/tested baseline, or validate your own matrix before
  rollout
- confirm dependency coordinates and module set are updated to `0.0.2`
- confirm custom exception advice still preserves intended app-module wire contracts

### `app-version`

- `GET /api/v1/version/check` still accepts the same headers
- only malformed semantic versions now return `400`; unregistered valid versions should return `200`
- `404` still means no policy rows exist for the service/platform
- `service_version` physical table/column names match the explicit mappings
- duplicate semantic-version rows have been cleaned before the uniqueness guard is applied
- rollout-ready rows are marked intentionally with `store_available`

### `storage-api`

- upload still returns the same JSON fields over HTTP
- direct controller/source consumers recompile against `ImageResponse`
- delete fails safely when persisted `storageType` no longer matches configured storage client keys
- delete leaves `DELETE_PENDING` when storage cleanup fails and succeeds on retry after recovery
- operator-owned recovery path for `DELETE_PENDING` is ready before production rollout

### `oauth-redirect`

- `GET /oauth/redirect/{provider}?redirectUri=...` still redirects correctly
- successful callback redirects frontend with `relayCode`
- replaying the same callback `state` fails
- callback behavior matches your chosen callback-binding mode
- app fails startup when oauth redirect is enabled but state store/provider wiring is incomplete
- cache/entity relay store behavior matches your single-node or multi-instance deployment model
