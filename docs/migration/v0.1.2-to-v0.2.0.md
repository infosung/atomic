# Release Migration Guide: `v0.1.2` -> `v0.2.0`

> Current minor-release migration guide for the `v0.2.0` line.

## Who Should Read This

Read this guide if you:

- already consume Atomic `0.1.2`
- want the first published release after `v0.1.2`
- plan to use the new Spring-free crypto helpers, JWT signing-key rotation support, or the updated
  OAuth redirect / PKCE / identity handoff model

If you are still moving from the pre-`0.1.x` line, first read
[Release Migration Guide: `v0.0.5` -> `v0.1.1`](v0.0.5-to-v0.1.1.md).

## Release Scope

`v0.2.0` is the first tagged release after `v0.1.2`.

It folds the unreleased `0.1.3` draft scope into a real release and adds the OAuth foundation and
redirect-relay changes that landed afterward.

| Area | Release impact |
|---|---|
| Version line | published artifact examples move from `0.1.2` to `0.2.0` |
| New utility module | `atomic.crypto` is now published as a standalone Spring-free helper module, including context-bound payload helpers such as `ContextBoundAeadEnvelopeCipher` |
| Security rotation | `JwtProvider` now accepts optional previous access/refresh signing keys for verification |
| OAuth foundation | `atomic.spring.oauth2` now exposes PKCE fields directly and returns richer normalized identity metadata |
| Redirect relay | `atomic.app.oauth.redirect` now keeps the browser/server relay model, manages PKCE server-side on the web API, and stores optional `resolvedIdentity` alongside `relayCode` |
| Release automation | the tag-and-release flow now expects the curated `docs/release-notes/v0.2.0.md` file |
| Published/runtime scope | event-log modules, DB vendor scope, and default OAuth redirect persistence behavior remain stable from `0.1.2` |
| Release history cleanup | `v0.1.3` was not a published tag; `v0.2.0` is the real release line that now carries that scope |

## Required Action

1. Bump Atomic artifact coordinates from `0.1.2` to `0.2.0`.
2. Add `atomic.crypto` only in hosts that need standalone crypto primitives or explicit key
   rotation helpers.
3. If you adopt the new context-bound payload helpers, keep the persisted contract explicit:
   - store the full `ContextBoundEncryptedPayload`
   - treat `keyVersion` as part of the encrypted payload contract, not transient request state
   - reconstruct the same `AeadEnvelopeContext` on decrypt
   - provide a resolver that can load current or previous keys by `keyId`
4. If you rotate JWT secrets, wire previous keys as verification-only lanes:
   - signing always uses the current key
   - previous keys are accepted only for token verification
   - newly issued tokens now include JWT `kid`
   - the Spring Boot property names are `access-key-id`, `refresh-key-id`,
     `previous-access-keys`, and `previous-refresh-keys`
5. If you use `atomic.spring.oauth2` directly for mobile/native/desktop orchestration, pass PKCE
   material explicitly through:
   - `OauthAuthorizationRequest.codeChallenge`
   - `OauthAuthorizationRequest.codeChallengeMethod`
   - `OauthTokenExchangeRequest.codeVerifier`
6. If you use `atomic.app.oauth.redirect`, keep the higher-level relay contract in mind:
   - browser-facing redirect API accepts optional `codeChallengeMethod`
   - the controller rejects client-supplied `codeVerifier`, `codeChallenge`, and provider-style
     PKCE parameters
   - callback redirects still return only `relayCode`
   - your login/session API should consume `resolvedIdentity` and prefer `providerSubject` for
     account binding and uniqueness
7. If your host app is still pinned to Spring Boot `4.0.3`, move to `4.0.5`.
8. If you mirror Atomic's repository workflows internally, align them with the current release
   automation:
   - Node 24 compatible action majors such as `actions/checkout@v5`
   - a curated release notes file at `docs/release-notes/v0.2.0.md`
9. Review the current release summary before rollout:
   - [Release Notes: `v0.2.0`](../release-notes/v0.2.0.md)

## What Does Not Change From `v0.1.2`

The following remain intentionally stable in `v0.2.0`:

- published event-log modules still include `atomic.event.log.ingest.api`
- relational DB support still covers `postgresql`, `mysql`, `mariadb`, and `oracle`
- `h2` remains test-compatibility only
- `atomic.app.oauth.redirect` still uses the `JPA-backed` default table path and the custom-table
  `legacy JDBC` fallback path
- final login, session issuance, authorization policy, and account binding still belong to the host
  application

This is a minor release because the public surface expanded materially, but it is still not a
runtime redesign of the app or event-log module families.

## Recommended Validation

After the version bump:

- run your normal integration coverage
- verify your host still treats Spring Boot `4.0.5` as the intended production baseline
- if you use the new crypto helpers, validate key rotation, context-bound envelope round-trips,
  and mismatched-context rejection
- if you use oauth redirect, rerun end-to-end login coverage for web, iOS, Android, macOS, and
  Windows handoff targets that your product supports
- verify your login API consumes `relayCode` and that `resolvedIdentity.providerSubject` is the
  provider account key you bind against
- if you mirrored the repository CI, confirm your publish workflow includes `atomic-crypto`
- if you operate release automation in-repo, confirm the new release-notes file exists before
  tagging

## Checklist

- bump dependency versions to `0.2.0`
- keep or move host baseline to Spring Boot `4.0.5`
- add `atomic.crypto` only where needed
- if you store encrypted payloads with `atomic.crypto`, keep `keyVersion` and the full
  `ContextBoundEncryptedPayload` intact
- review [Release Notes: `v0.2.0`](../release-notes/v0.2.0.md)
- if you bind external identities, prefer `providerSubject` and consume `resolvedIdentity` from
  the relay payload instead of reparsing provider data later
- if you copied repository release automation, keep Node 24 compatible action majors such as
  `actions/checkout@v5`
- if you copied repository release automation, add `docs/release-notes/v0.2.0.md`
