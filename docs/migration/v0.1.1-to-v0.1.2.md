# Release Migration Guide: `v0.1.1` -> `v0.1.2`

> Current patch migration guide for the `v0.1.2` line.

## Who Should Read This

Read this guide if you:

- already consume Atomic `0.1.1`
- want the current patch release line to be reflected consistently in docs, CI, and release automation
- rely on Atomic's tested Spring baseline and want the release-line expectation to be explicit

If you are still moving from the pre-`0.1.x` line, first read [Release Migration Guide: `v0.0.5` -> `v0.1.1`](v0.0.5-to-v0.1.1.md).

## Release Scope

`v0.1.2` is a patch release that aligns the current release line rather than introducing a new module family.

The key points are:

| Area | Release impact |
|---|---|
| Version line | published artifact examples move from `0.1.1` to `0.1.2` |
| Secure baseline continuity | current docs and CI are explicitly aligned to Spring Boot `4.0.5` as the secure tested baseline |
| CI workflow semantics | non-baseline compatibility lanes are isolated from the secure-baseline contract, and the duplicate `latest-boot` lane is removed |
| GitHub Actions runtime | repository workflows move to Node 24 compatible action majors such as `actions/checkout@v5` |
| Release automation | the tag-and-release flow now requires a curated `docs/release-notes/v0.1.2.md` file |
| Published/runtime scope | event-log modules, DB vendor scope, and OAuth redirect persistence behavior remain the same as `0.1.1` |

## Required Action

1. Bump Atomic artifact coordinates from `0.1.1` to `0.1.2`.
2. Keep your host app on Spring Boot `4.0.5` if you follow Atomic's tested release line.
3. If your host app is still pinned to Spring Boot `4.0.3`, move to `4.0.5`.
   Why:
   - the current secure line still tracks the Spring fixes for `CVE-2026-22732` and `CVE-2026-22735`
   - `4.0.5` keeps you on the fixed Spring Framework `7.0.6` / Spring Security `7.0.4` path
4. If you mirror Atomic's repository workflows internally, align them with the current release automation:
   - Node 24 compatible action majors such as `actions/checkout@v5`
   - a curated release notes file at `docs/release-notes/v0.1.2.md`
5. Review the current release summary before rollout:
   - [Release Notes: `v0.1.2`](../release-notes/v0.1.2.md)

## What Does Not Change From `v0.1.1`

The following remain intentionally stable in `v0.1.2`:

- published event-log modules still include `atomic.event.log.ingest.api`
- relational DB support still covers `postgresql`, `mysql`, `mariadb`, and `oracle`
- `h2` remains test-compatibility only
- `atomic.app.oauth.redirect` still uses the `JPA-backed` default table path and the custom-table `legacy JDBC` fallback path

This is a patch alignment release, not a runtime surface redesign.

## Recommended Validation

After the version bump:

- run your normal integration coverage
- verify your host still treats Spring Boot `4.0.5` as the intended production baseline
- if you mirrored the repository CI, confirm your non-baseline lanes do not enforce the secure baseline contract
- if you operate release automation in-repo, confirm the release-notes file exists before tagging

## Checklist

- bump dependency versions to `0.1.2`
- keep or move host baseline to Spring Boot `4.0.5`
- review [Release Notes: `v0.1.2`](../release-notes/v0.1.2.md)
- if you copied repository release automation, keep Node 24 compatible action majors such as `actions/checkout@v5`
- if you copied repository release automation, add `docs/release-notes/v0.1.2.md`
