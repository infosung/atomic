# Release Migration Guide: `v0.0.5` -> `v0.1.1`

> Historical release-scoped guide for the `v0.1.1` line.
>
> If you are already on `v0.1.1`, continue with [Release Migration Guide: `v0.1.2` -> `v0.1.3`](v0.1.2-to-v0.1.3.md).

## Who Should Read This

Read this guide if you:

- already consume any published `com.infosung:*` Atomic artifact and will bump to `0.1.1`
- want to adopt the event-log stack
- rely on the published module list in README or `docs/usage`

## Release Scope

`v0.1.1` was the first stabilized patch target in the `0.1.x` release line where the event-log stack
became documented and published as a first-class part of Atomic.

This migration is not only a version-coordinate bump. It also changes the tested Spring security
baseline for the release line.

The main release-level changes are:

| Area | Release impact |
|---|---|
| Version line | all published artifact examples move from `0.0.5` to `0.1.1` |
| Event log | `atomic.event.log`, `parquet`, `iceberg`, `duckdb`, `spring.web`, and `ingest.api` are now treated as first-class published modules in docs and release automation |
| Publish automation | `atomic-event-log:ingest-api` is now part of the Maven Central publish workflow |
| Spring baseline and security | tested Spring baseline moves from Spring Boot `4.0.3` to Spring Boot `4.0.5` to pick up the OSS fixes for `CVE-2026-22732` and `CVE-2026-22735` |
| Relational DB support | app DB assets and automated verification now cover `postgresql`, `mysql`, `mariadb`, and `oracle`; `h2` stays test-compatibility only |
| OAuth redirect persistence | default `store.type=entity` path is now JPA-backed on the shipped `atomic_oauth_relay_code` table; custom `table-name` keeps the legacy JDBC fallback |
| Oracle release validation | the focused Oracle workflow `.github/workflows/oracle-compatibility.yml` remains available, and the publish release gate re-runs the same focused Oracle checks before publication |
| Documentation | onboarding docs now include an event-log adoption path instead of only app/security/storage tracks |

## Required Action

1. Bump all Atomic artifact coordinates you use from `0.0.5` to `0.1.1`.
2. If your host app uses Atomic's Spring baseline, move from Spring Boot `4.0.3` to Spring Boot `4.0.5`.
   Why:
   - Spring Boot `4.0.3` resolves to Spring Framework `7.0.5` and Spring Security `7.0.3`
   - those versions are within the affected ranges for `CVE-2026-22735` and `CVE-2026-22732`
   - Spring Boot `4.0.5` resolves to the corresponding OSS fix line: Spring Framework `7.0.6` and Spring Security `7.0.4`
   - upgrading Atomic alone does not fix this if your host app still explicitly pins Spring Boot `4.0.3`
3. Review the curated release summary before rollout:
   - [release notes](../release-notes/v0.1.1.md)
4. If you publish or consume the event-log HTTP ingest API, switch to the published artifact:
   - `com.infosung:atomic.event.log.ingest.api:0.1.1`
5. If your team follows README or `docs/usage` dependency snippets, refresh local setup snippets to
   the `0.1.1` examples shipped in this release.
6. If you use `atomic-app` relational modules, align your DB expectations with this release line:
   - official shipped SQL assets and automated verification cover `postgresql`, `mysql`, `mariadb`, and `oracle`
   - `h2` remains test-compatibility only
   - repository automation verifies Oracle on the Oracle Free 23 line; if you operate another Oracle line, keep equivalent host CI verification before rollout
7. If you use `atomic.app.oauth.redirect` with `store.type=entity`, note the persistence contract:
   - default table `atomic_oauth_relay_code` now uses the JPA-backed store path
   - custom `atomic.app.oauth.redirect.store.entity.table-name` intentionally remains on the legacy JDBC-backed store path to preserve the public runtime contract
   - `store.fail-fast=false` can fall back to the in-memory relay store, which is process-local per instance and is not multi-instance safe

## Why The Spring Baseline Changed

The Spring baseline move is deliberate and not cosmetic.

- the previous tested baseline in this repository was Spring Boot `4.0.3`
- that baseline resolved to Spring Framework `7.0.5` and Spring Security `7.0.3`
- Spring's official advisories mark those lines as affected by:
  - `CVE-2026-22732`
  - `CVE-2026-22735`
- the updated tested baseline is Spring Boot `4.0.5`, which resolves to Spring Framework `7.0.6`
  and Spring Security `7.0.4`

This was chosen because it fixes the known Spring advisories while preserving the same Boot major/minor
line and minimizing host behavior changes.

What we intentionally did not do:

- we did not add behavior-changing Spring Security workarounds in Atomic itself
- we did not force host applications onto a custom Spring override outside the Boot patch line

That tradeoff keeps the user-visible runtime behavior stable for hosts that move to the new baseline.

## Event Log Adoption Path

If you are adopting the event-log stack for the first time, the recommended path is:

1. `atomic.event.log`
2. `atomic.event.log.parquet`
3. one ingress path:
   - `atomic.event.log.ingest.api` for the official Spring MVC ingest API
   - `atomic.event.log.spring.web` to bridge existing `atomic.spring.web` API logs
4. optional lakehouse extensions:
   - `atomic.event.log.iceberg`
   - `atomic.event.log.duckdb`

## Existing App/Starter Consumers

For teams already using `atomic.app`, `atomic.starter`, `atomic.storage`, `atomic.spring.web`,
`atomic.spring.security`, `atomic.spring.idempotency`, `atomic.spring.oauth2`, or `atomic.heartbeat`:

- this release line does not introduce a new mandatory property rename
- the expected host action is mainly:
  - version bump
  - Spring Boot baseline alignment to `4.0.5` where you follow Atomic's tested baseline
  - doc refresh
- re-run your normal integration coverage after the version bump, especially around:
  - app-module endpoints
  - security/idempotency filters
  - oauth callback flows
  - any custom exception mapping

## Relational DB Scope

For `atomic-app:app-version`, `atomic-app:storage-api`, and `atomic-app:oauth-redirect`:

- official shipped SQL assets and automated verification cover `postgresql`, `mysql`, `mariadb`, and `oracle`
- `h2` is included for test compatibility only
- release automation keeps a dedicated focused Oracle workflow (`oracle-compatibility.yml`) and re-runs the same Oracle-focused checks in the publish release gate
- startup preflight now relies on portable JDBC metadata instead of PostgreSQL-specific catalog queries, but any database outside the official list should still be validated in your host CI before production rollout

## OAuth Redirect Persistence Compatibility

`atomic.app.oauth.redirect` keeps the public `store.type=entity` contract, but its internal path is now split more clearly:

- default shipped table contract (`atomic_oauth_relay_code`) uses the JPA-backed store path
- custom `atomic.app.oauth.redirect.store.entity.table-name` keeps the legacy JDBC-backed store path so existing table-name customization does not silently break
- `store.fail-fast=false` still means startup can fall back to the in-memory relay store; treat that as local or intentionally single-node only

## Checklist

- bump dependency versions to `0.1.1`
- move host Spring Boot baseline from `4.0.3` to `4.0.5` if you rely on Atomic's tested release line
- do not assume upgrading Atomic alone fixes Spring advisories when your host still pins Spring Boot `4.0.3`
- confirm your release docs or internal templates no longer point to `0.0.5`
- review the [release notes](../release-notes/v0.1.1.md)
- if you need official ingest API publishing, use `atomic.event.log.ingest.api`
- if you rely on official Oracle support, keep `.github/workflows/oracle-compatibility.yml` or an equivalent focused Oracle gate in your release process
- run your normal CI/integration verification before rollout
