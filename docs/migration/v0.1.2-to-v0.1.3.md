# Release Migration Guide: `v0.1.2` -> `v0.1.3`

> Current patch migration guide for the `v0.1.3` line.

## Who Should Read This

Read this guide if you:

- already consume Atomic `0.1.2`
- want the current patch release line to be reflected consistently in docs, CI, and release
  automation
- plan to use the new Spring-free crypto helpers or JWT signing-key rotation support

If you are still moving from the pre-`0.1.x` line, first read
[Release Migration Guide: `v0.0.5` -> `v0.1.1`](v0.0.5-to-v0.1.1.md).

## Release Scope

`v0.1.3` is a patch release that aligns the current release line while adding a new reusable crypto
module and security rotation helpers.

| Area | Release impact |
|---|---|
| Version line | published artifact examples move from `0.1.2` to `0.1.3` |
| New utility module | `atomic.crypto` is now published as a standalone Spring-free helper module |
| Security rotation | `JwtProvider` now accepts optional previous access/refresh signing keys for verification |
| CI workflow semantics | publish workflow module order now includes `atomic-crypto` and release docs reference `v0.1.3` |
| Release automation | the tag-and-release flow now requires a curated `docs/release-notes/v0.1.3.md` file |
| Published/runtime scope | event-log modules, DB vendor scope, and OAuth redirect persistence behavior remain the same as `0.1.2` |

## Required Action

1. Bump Atomic artifact coordinates from `0.1.2` to `0.1.3`.
2. Add `atomic.crypto` only in hosts that need standalone crypto primitives or explicit key
   rotation helpers.
3. If you rotate JWT secrets, wire previous keys as verification-only lanes:
   - signing always uses the current key
   - previous keys are accepted only for token verification
   - newly issued tokens now include JWT `kid`
   - the Spring Boot property names are `access-key-id`, `refresh-key-id`,
     `previous-access-keys`, and `previous-refresh-keys`
4. If your host app is still pinned to Spring Boot `4.0.3`, move to `4.0.5`.
5. If you mirror Atomic's repository workflows internally, align them with the current release
   automation:
   - Node 24 compatible action majors such as `actions/checkout@v5`
   - a curated release notes file at `docs/release-notes/v0.1.3.md`
6. Review the current release summary before rollout:
   - [Release Notes: `v0.1.3`](../release-notes/v0.1.3.md)

## What Does Not Change From `v0.1.2`

The following remain intentionally stable in `v0.1.3`:

- published event-log modules still include `atomic.event.log.ingest.api`
- relational DB support still covers `postgresql`, `mysql`, `mariadb`, and `oracle`
- `h2` remains test-compatibility only
- `atomic.app.oauth.redirect` still uses the `JPA-backed` default table path and the custom-table
  `legacy JDBC` fallback path

This is a patch alignment release with a small reusable utility expansion, not a runtime redesign of
the app module family.

## Recommended Validation

After the version bump:

- run your normal integration coverage
- verify your host still treats Spring Boot `4.0.5` as the intended production baseline
- if you use the new crypto helpers, validate key rotation and envelope round-trips
- if you mirrored the repository CI, confirm your publish workflow includes `atomic-crypto`
- if you operate release automation in-repo, confirm the new release-notes file exists before
  tagging

## Checklist

- bump dependency versions to `0.1.3`
- keep or move host baseline to Spring Boot `4.0.5`
- add `atomic.crypto` only where needed
- review [Release Notes: `v0.1.3`](../release-notes/v0.1.3.md)
- if you copied repository release automation, keep Node 24 compatible action majors such as
  `actions/checkout@v5`
- if you copied repository release automation, add `docs/release-notes/v0.1.3.md`
